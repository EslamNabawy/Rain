# Risk Register

Last updated: 2026-08-21

## Purpose

This register manages risks discovered through [[Original Audit]], [[Current Architecture]], [[Master Roadmap]], and [[Technical Debt Register]].

Risk is tracked separately from debt:

- Debt is a known structural weakness.
- Risk is the chance and impact of that weakness causing project, user, security, or operational failure.

Related: [[Risk Categories]], [[Risk Matrix]], [[BLOCKERS]], [[Blocker Resolution Plan]], [[Technical Debt Register]], [[Debt Prioritization]], [[Launch Readiness]], [[Production Readiness]], [[2026-06-05 Senior Audit Remediation Plan]].

## Risk Scoring Model

| Field | Values |
| --- | --- |
| Impact | Low, Medium, High, Critical |
| Probability | Low, Medium, High |
| Severity | Low, Medium, High, Critical |
| Status | Open, Watching, Mitigating, Mitigated, Accepted, Closed |

Severity rule:

- Critical: public launch blocker, security blocker, or core feature unusable.
- High: production-readiness blocker or likely severe user impact.
- Medium: meaningful quality, maintenance, or support risk.
- Low: cleanup or narrow edge-case risk.

## 2026-06-06 Diagnostic Risk Updates

- R-014 update: `rain-diagnostics-2026-06-06T170224-576454Z.json` showed a current-session late callee ICE write denied after the direct data lane had already connected. The local mitigation keeps the active data-peer room alive until session cleanup while retaining canonical `callerICE`/`calleeICE` ownership. This is a lifecycle fix, not a Firebase rules broadening.
- R-014 update 2026-06-07: delete-account tombstone denial exposed a live RTDB rules/data-shape risk. The `users/{username}` rule now permits legacy rows with no `uid` to be tombstoned only by the authenticated `$username@rain.local` user while preserving immutable ownership for rows that already have `uid`. The updated rules were deployed to and read back from `rain-8fb4b-default-rtdb`.
- R-021 update: pending logout no longer waits for backend cleanup before ending protected-session authority. Runtime clears local session data first for logout, preserves the session for non-destructive delete preflight failures such as bad password, and destructive account deletion now invokes backend/Auth deletion before local session clear so the delete button cannot degrade into plain logout.
- R-021 update 2026-06-07: delete-account required tombstone failure now preserves the signed-in session and local identity. Runtime no longer starts shutdown before backend/Auth deletion, optional RTDB cleanup runs best-effort after the tombstone boundary, and Settings shows a modal error for delete failures. A follow-up provider fix keeps `RuntimeController.deleteAccount` from publishing global startup loading during password/tombstone preflight, preventing wrong-password and pre-tombstone failures from unmounting Settings before feedback can render. A further UI/state fix switches to a full-screen `deletingAccount` overlay only after password verification succeeds, hides navigation, keeps the current route mounted for backend-failure recovery, and records a same-device deleted-username marker so a later login can say the account was deleted instead of only showing Firebase's generic credential copy. The latest auth-boundary fix cancels account-scoped RTDB listeners and active protocol/data-room sessions before Firebase Auth deletion, preventing stale permission-denied listener errors during the login-screen transition. The live-rules follow-up deploy/readback closes the specific missing-uid backend tombstone denial path; the reported Android account still needs a retry before removing the bug from watch.
- R-022 update: `AppStartupState` now requires a non-null runtime for `ready` and treats runtime loading as blocked startup even when Riverpod exposes a previous runtime value. The follow-up logout path then transitions to signed-out after local session clear instead of staying on global loading while cleanup is blocked, while delete-account waits for backend/Auth deletion before local sign-out. ## Escalation Rules

- Any Critical security risk blocks public distribution.
- Any Critical call reliability risk blocks public launch.
- Any Critical update/version risk blocks backend rule changes that can affect old clients.
- Any Critical release-gate risk blocks cloud release promotion.
- Blockers must never stop progress; use [[Blocker Resolution Plan]] to route parallel work.

## Register Definition Of Done

- Every risk has impact, probability, severity, mitigation, detection strategy, owner, and links to roadmap/debt.
- Every Critical risk maps to at least one blocker in [[BLOCKERS]] or explicit acceptance in [[Launch Readiness]].
- Mitigated risks update [[Technical Debt Register]], [[Audit Resolution Tracker]], and [[Project Memory]] when durable facts change.
