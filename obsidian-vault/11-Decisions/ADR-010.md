# ADR-010: Accept Plaintext Local Drift Storage For Current Scope

Date: 2026-06-05

## Context

Rain stores chat history, outgoing queued messages, file-transfer metadata, local file paths, identity, friends, and connection memory through Drift/SQLite in `packages/rain_core`.

Phase 5 of [[2026-06-05 Senior Audit Remediation Plan]] required an explicit decision because current code stores sensitive local content but the project also uses privacy language around private peer-to-peer communication.

Context7 Drift documentation was checked on 2026-06-05. Drift supports encrypted databases only through explicit database-opening/key setup; encryption is not automatic.

Related: [[Privacy Review]], [[Security Roadmap]], [[Risk Register]], [[Technical Debt Register]], [[Launch Readiness]].

## Problem

The implementation and the product claims must match.

Current repository evidence:

- `messages.content` is a Drift text column.
- `queued_messages.content` is a Drift text column.
- `file_transfers.fileName` and `file_transfers.localPath` are Drift text columns.
- `MessageStore`, `OfflineQueue`, and `FileTransferStore` write those values directly.
- `_openRainDatabase()` uses normal Drift native SQLite setup and does not configure a database encryption key.

If Rain claims local message encryption without implementing database encryption, key management, and migration proof, the security model is misleading.

## Options

1. Accept plaintext local storage and document the threat model.
2. Implement encrypted local storage now, including key management and migration from existing plaintext databases.

## Decision

Choose Option 1 for the current phase.

Rain accepts plaintext local Drift/SQLite storage as an explicit current-scope limitation. Local device compromise, direct filesystem access to app data, malware on the device, and forensic copies of the app data directory are not protected by current app-layer database encryption.

Rain must not claim encrypted local message history, encrypted local queue storage, or encrypted file-transfer metadata until Option 2 is implemented and validated.

## Consequences

- SAR-005 is accepted/documented, not technically fixed.
- Strong local privacy claims remain blocked.
- Diagnostics privacy work remains separate: diagnostics still must not export message text, file bytes, raw SDP, raw ICE, tokens, passwords, or ciphertext payloads.
- Future encryption work must be planned as its own phase with dependency selection, key generation/storage/rotation policy, lost-key behavior, plaintext-to-encrypted migration, interrupted-migration recovery, and tests.
- Release, support, privacy, and roadmap notes must describe the current limitation accurately.
