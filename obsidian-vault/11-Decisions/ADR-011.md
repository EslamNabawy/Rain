## Context

The 2026-08-27 Windows diagnostic export `rain-diagnostics-2026-08-27T204636-059426Z.json` exposed that current `RainDebugLogService` events carry no flow correlation. A 200-event export for one call failure showed 55 `ui_state` events, 25 `operation_*` events, 1 call summary, and 1 lastCrash, but no way to tie "the user tapped the onboarding submit button" to "the call failed 11 seconds later."

Without correlation, every bug repro requires the user to narrate what they did. The current export is useful for crash triage but is not sufficient for *what-happened* debugging.

Related: [[Diagnostics And Logging]], [[Risk Register]], [[Technical Debt Register]], [[Project Memory]], [[Authentication]].

## Problem

Rain's current diagnostic stream is a flat, unordered event log scoped to one session. There is no per-flow identifier, so a debug query like "show me everything related to the call that failed at 20:46:10" requires manual timestamp correlation across categories.

The 2026-08-27 plan `docs/plans/2026-08-27-rain-fix-and-tracing-design.md` defined a unified tracing system with `traceId` + `spanId` per user flow, propagated via `Zone` and Riverpod. The 2026-08-27 plan also defined `ThrottledProviderObserver`, `AppNavigationObserver`, and `InteractionTrace` helpers as the first wire-up.

## Options

1. Adopt the plan as-is: add `TraceContext` (Zone-based OTel-lite), wire `traceId` into `register` and `startVoiceCall`, swap `RainDebugProviderObserver` for `ThrottledProviderObserver`, add `AppNavigationObserver` to GoRouter.
2. Wait until Drift-backed event persistence is also designed; do full Track B from the plan at once.
3. Skip tracing; rely on existing event log + manual correlation.

## Decision

Choose Option 1 with the following scoping:

- Add the four scaffold files into `apps/rain/lib/infrastructure/diagnostics/tracing/` (`trace_context.dart`, `interaction_logger.dart`, `app_navigation_observer.dart`, `throttled_provider_observer.dart`).
- Skip `voice_call_tracing_patch.dart`; its `VoiceFailureTaxonomy` enum competes with the existing `CallErrorClassifier` and the design's SDP fix predates the 2026-06-08 `VoiceCallStateCoordinator` work that owns call state.
- Add `traceId` to `IdentityController.register` and `RainRuntimeController._startCall` (covers voice and video) only.
- Do **not** add `traceId` to heartbeat, ICE writes, or Firebase operations in this slice. The plan's Track A fixes (presence grace, parallel subscription cancel, SDP fix) are still open and tracked separately.
- Do **not** add Drift persistence of events. The current in-memory ring buffer in `RainDebugLogService` is unchanged.

The `InteractionLogger` widget and `BuildContext.logTap` extension are kept in the scaffold but unused in this slice; they document the intended capture path for the next slice and are not removed to keep the scaffold intact.

The `ThrottledProviderObserver._noisyProviders` set uses `ProviderObserver.provider.runtimeType.toString()` as the key, which depends on Riverpod internals. The keys `Provider<ConnectionDiagnostics>` and `NotifierProvider<PeerConnectivityController, Map<String, PeerConnectivitySnapshot>>` are best-effort; mismatches are silent. The observer also drops updates where `hashCode` matches the last emit, which assumes structural equality is implemented by the value type. `PeerConnectivitySnapshot` and `ConnectionDiagnostics` do not override `==`/`hashCode`; identity-equal updates still emit, but `hashCode` collisions across distinct values would silently drop legitimate updates. This is documented as accepted risk in the new risk entry.

## Consequences

- `register` and `startVoiceCall` events share a `traceId` for the duration of each flow. Cross-event queries by `traceId` are now possible in any export.
- The `ThrottledProviderObserver` reduces provider event volume for two known noisy providers. Other providers emit at their existing rate. Net effect: small reduction in event count; no behavior change for app flows.
- `AppNavigationObserver` records every GoRouter push/pop/replace. Existing `ui_state/navigation` events are unchanged; new `interaction/navigation` events with `traceId` are added.
- The four scaffold files carry the existing scaffold's documented limitations (PII handling, no PII in tap targets, hash-based throttling). These are accepted; full sanitizer coverage is a separate decision.
- Drift persistence of `app_events`, `traceSummaries`, and a debug overlay UI (`DiagnosticsSheet`, `/debug/traces`) are explicitly deferred. They require separate architecture and security review.
- A new technical-debt item (TD-023) records the traceId coverage gaps; a new risk (R-023) records the throttling hash-collision risk.
